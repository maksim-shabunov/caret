# Contributing

Bug reports are the most useful thing you can send, and a good one is short: what
you typed, what Caret did, what you expected, and which layouts you have
installed. Settings › Privacy has a history of recent corrections, which is
usually the whole story.

## Getting set up

```sh
git clone https://github.com/maksim-shabunov/caret.git
cd caret
swift test
./build.sh --install --run
```

Needs macOS 15 and Swift 6.2 (Xcode 26). There is no Xcode project; open the
folder in whatever you like.

## Changing a correction rule

This is where most of the interesting work is, and it has one house rule:
**measure before and after.**

Every threshold in `Sensitivity`, `PlausibilityRule` and `CorrectionEngine` was
chosen by running against the corpora in `Sources/CaretCore/LanguageModels` —
about 51,000 Russian words and 29,000 English ones. A rule that looks right on
half a dozen hand-picked examples can easily be wrong hundreds of times across
the corpus, and this has already happened at least once: a shape-based rule that
read convincingly on eight examples turned out to cost 247 real corrections,
because every Russian word beginning with `б` reaches the keyboard with a
leading comma.

So if you are changing when Caret does or does not act:

1. Write the failing case as a test first.
2. Sweep the corpus for what your change costs, not only what it fixes. There is
   no script for this — a throwaway test that walks the word list and counts is
   the usual way, and takes about twenty lines.
3. Put the number in the commit message and in the code comment. "247 real
   corrections against the dictionary's 24" is worth more to the next person
   than any amount of prose.

A missed correction is invisible. A wrong one is infuriating. When the evidence
is genuinely balanced, silence wins.

## Tests

```sh
swift test
```

215 of them, and none need a particular keyboard layout installed — the layouts
are a committed snapshot (`Tests/CaretCoreTests/Layouts.json`, regenerated by
`Tools/DumpLayouts.swift`). They do use the real macOS spell checker and the
real character models, deliberately: the thresholds were measured against those,
so a test built on toy data would prove nothing about them.

## Style

Follow what is already there. The one thing worth stating explicitly is the
comments: they explain *why*, and particularly why an obvious alternative was
rejected. Several of them describe bugs that shipped. Keep that — a comment
saying what the code does is noise, and a comment saying what it must never do
again is the most valuable line in the file.

## Pull requests

Keep them focused, keep the tests green, and say what you measured. If you are
planning something large, open an issue first so nobody writes the same thing
twice.
